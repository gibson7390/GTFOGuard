Implement RiskScorer support for path_anomaly detections.

Context:

The Orchestrator phase is complete and validated.

Integration testing revealed that PathAnomalyDetector detections currently fall through RiskScorer's default unknown-type branch.

Current behavior:

[LOW] score=2 path_anomaly /tmp/
reason: Unknown detection type 'path_anomaly'

This is not an Orchestrator issue.

The Orchestrator correctly passes PathAnomalyDetector results into RiskScorer.

The gap is that RiskScorer was implemented before PathAnomalyDetector existed and therefore has no explicit scoring rule for detection_type="path_anomaly".

Goal:

Extend RiskScorer so path_anomaly detections receive an intentional severity, score, and explanation rather than being treated as an unknown detection type.

Requirements:

1. Modify only the scoring layer.
2. Do not modify PathAnomalyDetector.
3. Do not modify the Orchestrator.
4. Do not modify existing detector behavior.
5. Preserve existing GTFOBins scoring behavior.
6. Preserve existing command-line scoring behavior.
7. Maintain separation of concerns.

Architecture constraints:

GOOD:

    ...

BAD:

if detection.snapshot.exe.startswith("/tmp"):
    ...

RiskScorer should score based on detector output, not reimplement detector logic.

The detector has already determined that the path is suspicious.

RiskScorer should trust detector output and assign an appropriate risk classification.

Scoring requirements:

- Add explicit support for detection_type="path_anomaly".
- Provide a severity.
- Provide a numeric score.
- Provide a human-readable explanation.
- Remove the "Unknown detection type" fallback for path_anomaly detections.
